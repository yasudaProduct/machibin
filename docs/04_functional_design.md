## 4. 機能詳細

### 4.1 FR-01 会員登録・認証

認証（サインアップ・サインイン・セッション）はClerkに委譲する。フローの詳細は 10 認証・認可設計書。本書では業務ルールのみ定める。

**業務ルール**

1. 登録に必要な情報はメールアドレス（Clerk保持）とニックネームのみ。本名・写真・生年月日は収集しない（BD-03、NFR-PR02）。
2. Clerkの `user.created` Webhook受信時に `profiles` の空レコードを作成する。ニックネーム設定・13歳以上確認・利用規約同意（SCR-10 → API-11）が完了するまで `onboardingCompleted=false` とし、投函等の主要機能は利用できない（画面側でSCR-10へ誘導）。
3. 13歳以上であることの同意が得られない場合は登録を完了させない（BD-03）。
4. 退会（API-12）は、DB側の削除・匿名化（06 §7.1）→ Clerkユーザー削除の順で実行する（10 §6）。

**例外**

| 事象 | 挙動 |
| --- | --- |
| Webhook未達でprofilesが存在しないままAPIコール | 認証MWで検出し、その場でprofiles空レコードを補完作成（自己修復） |
| 退会済みトークンでのアクセス | 401 UNAUTHORIZED |

### 4.2 FR-02 プロフィール管理

**入力**（API-11）: ニックネーム、アバターID（プリセット。BD-07）、居住エリア（市区町村コード＋表示名。任意）、ひとこと自己紹介（任意）。

**処理**

1. 文字数チェック（PRM-08、PRM-09）。前後空白はトリムする。
2. 居住エリアはJIS X 0402の市区町村コード5桁で受領する。**市区町村より細かい情報（町名・番地）は項目自体が存在しない**（NFR-PR02）。
3. 初回設定時は `ageConfirmed` / `tosAgreed` を受理し、日時を記録する。

**業務ルール**

- 居住エリアは差出人エリア表示（FR-05）の元ネタになる。未設定の場合、受信者には差出人エリアを表示しない。
- ニックネームの重複は許容する（一意性は不要。ユーザー間にIDを見せる導線がないため）。

### 4.3 FR-03 スポット投函

**入力**（API-20 / SCR-03）: 場所名、緯度経度（クライアントで丸め済み）、カテゴリ（CD-01）、コメント、Turnstileトークン。

**処理**

1. Turnstileトークンを検証する（NFR-S03）。失敗時は403。
2. 当日（JST 0時起算）の投函数がPRM-05未満であることを確認する。超過時は422。
3. 入力値検証: 場所名1〜50文字、コメントPRM-01〜PRM-02、カテゴリはCD-01のいずれか、座標は日本国内の有効範囲。
4. **座標の再検証**: 受領座標からgeohash（precision=PRM-04）を計算し、セル中心と一致しない場合はサーバー側でセル中心に丸め直す（NFR-PR01。詳細は 11 §3）。
5. `spots` に登録する（kind='normal'、status='active'）。
6. 続けて交換抽選（FR-04）を同一トランザクションで実行する。

**出力**: 登録スポット＋交換結果（配達予定時刻 or pending）。

**例外**

| 事象 | 挙動 |
| --- | --- |
| 同一idempotencyKeyの再送 | 初回結果をそのまま返す（二重投函防止） |
| 停止中（suspended）ユーザー | 403 ACCOUNT_SUSPENDED |

**業務ルール**

- 投稿は編集不可（Phase 1）。誤投稿は本人削除機能も設けず、通報・運営対応で扱う（シンプル化。必要になればPhase 2で検討）。
- 住宅地・自宅付近の投稿を控えるよう投函画面に注意文言を常設する（R-03対応。文言は 05 SCR-03）。

### 4.4 FR-04 ランダム交換

**処理**（API-20内、投函の直後に実行）

1. 抽選クエリ（06 §6.1）で候補を1件選ぶ。除外条件:
   - 自分が投稿したスポット
   - 過去に受信済みのスポット（IX-05）
   - ブロック関係（双方向）にある相手のスポット
   - status≠active のスポット
2. 候補あり → `exchanges` を status='scheduled'、deliver_at=**次の配達ウィンドウ**で作成する。
3. 候補なし → status='pending' で作成し、配達バッチ（JOB-02）が再抽選する。

**deliver_atの決定ルール（BD-01）**

- 投函時刻（JST)より後の、最初の PRM-03 の時刻（7:00 / 19:00）とする。
  - 例: 10:30投函 → 当日19:00配達、21:00投函 → 翌日7:00配達、6:50投函 → 当日7:00配達。
- ウィンドウ直前の投函は遅延がごく短くなるが許容する(配達演出はアプリ側で最低限の演出時間を確保)。体験調整はPRM-03の変更で行う。

**業務ルール**

- スポットは「消費」されない（Postcrossing方式。02 §5.1補足）。同一スポットが複数ユーザーに配られ得るが、同一ユーザーへの再配達はない。
- シードスポット（kind='seed'）は通常投稿と同格でプールに含まれ、在庫不足時の実質的な受け皿となる（FR-10）。
- 交換の1対1性: 1投函＝1交換はIX-06（trigger_spot_id UNIQUE）で保証する。

### 4.5 FR-05 受信・配達

**処理**（JOB-01。詳細は 08 バッチ設計書）

1. 配達ウィンドウ時刻に、deliver_at到達済みの scheduled 交換を配達確定する。
2. 配達時に `collection_items` へスナップショットを生成する(BD-06)。差出人エリア（sender_area_label）は投稿者の居住エリア表示名（シードは投入時指定値）を複製する。
3. 受信者へNT-02（配達完了通知）を送信する。

**受信スポットの表示内容**（API-41 / SCR-05）: 場所名・位置（丸め済み座標）・カテゴリ・コメント・差出人エリア（市区町村レベル、未設定なら非表示）。**差出人個人を特定できる情報は一切表示しない**（NFR-PR02）。

**例外**

| 事象 | 挙動 |
| --- | --- |
| 配達時点で割当スポットがhidden/deletedになっていた | 当該交換をpendingに戻し、JOB-02で再抽選（低品質スポットを配達しない） |
| 受信者が退会済み | 交換を終端（配達しない） |
| 受信者が停止中 | 配達を次回ウィンドウへ持ち越し |

### 4.6 FR-06 リアクション

**入力**（API-43 / SCR-05）: 種別（CD-07: want_to_go / visited）、報告コメント（visitedのみ任意。PRM-07）。

**処理**

1. 対象の場所帳アイテムが自分のものであることを確認（他人のIDは404）。
2. 同一交換×同一種別の既存リアクションがあれば409。
3. `reactions` に登録する。
4. 原本スポットが存在し、投稿者が有効（active）かつ通知許可（notify_reaction）の場合、NT-03を送信する。

**業務ルール**

- リアクションの取り消しはPhase 1では提供しない。
- want_to_go と visited は両方付与できる（順不同）。
- リアクション数は投稿者本人にのみ累計表示し(visitedCount)、ランキング等での公開はしない（FR-06、01 §3.2）。

### 4.7 FR-07 もらった場所帳

**処理**

- 一覧（API-40 cursor / SCR-07): 配達日時の降順。訪問済み/未訪問でフィルタ可能。
- 地図（API-40 bbox / SCR-06）: 表示領域内のアイテムを返す（上限200件）。
- 訪問ステータス（API-42）: visited_at の設定/解除。訪問済みはスタンプ等の達成表現を付与（表現は 05 画面設計書）。
- 自分の投函一覧（API-21 / SCR-11）: 投函したスポットと「行ってきた」された累計（visitedCount）を本人にのみ表示。

**業務ルール**

- 場所帳はスナップショット（TBL-05）を表示するため、原本の削除・投稿者退会後も閲覧できる（BD-06）。
- 原本がhidden化された場合もスナップショットは残す。ただし通報して自分が非表示にしたアイテムは一覧から除外する（Phase 1では通報＝当該アイテムの非表示扱いとする）。

### 4.8 FR-08 通報・ブロック

**入力**（API-50 / SCR-09）: 対象種別（spot / user）、対象ID、理由（CD-04）、詳細（任意500文字）。

**処理**

1. `reports` に登録する。spot通報の場合は投稿者を解決して `target_user_id` にも記録する。
2. `blocks` に「通報者→対象ユーザー」の除外関係を登録する（既存なら何もしない）。**以降のマッチングで双方向に除外される**（FR-08「マッチ永久除外」）。
3. 対象スポットへの未対応（open）通報件数がPRM-06以上になったら、スポットを自動的に `hidden` にする。
4. 運営はAPI-61で通報を確認し、API-62で対応（none / hide_spot / suspend_user）を記録・実行する（NFR-O01、BD-04）。

**業務ルール**

- 通報はキャンセル不可。同一ユーザーによる同一対象への重複通報は登録するが、自動非表示のカウントは通報者単位で1とする。
- ブロック解除機能はPhase 1では提供しない（永久除外）。
- suspended になったユーザーの投稿は一括で `hidden` にする（API-62 / API-64 の付随処理）。

### 4.9 FR-09 通知

通知の種別・文面・配信方式は 09 通知設計書を正とする。本書では業務ルールのみ定める。

1. 通知は3種（NT-01 交換成立 / NT-02 配達完了 / NT-03 リアクション）。種別ごとにユーザーが受信可否を設定できる（TBL-01のnotify_*、API-13）。
2. 通知が配信不能でも業務処理（配達・リアクション登録）は成立させる（通知はベストエフォート）。
3. マーケティング目的のプッシュはPhase 1では送らない。

### 4.10 FR-10 シードスポット投入（運営機能）

**入力**（API-60）: スポット配列（最大100件/回）＋差出人エリア表示名。

**処理**

1. admin権限を確認する（BD-04、10 §7）。
2. 通常投稿と同一のバリデーション（コメント最低文字数・座標丸め再検証・カテゴリ）を適用する（FR-10「同一の表示・品質基準」）。
3. `kind='seed'` で登録する。author_user_idはNULL(運営者個人に紐付けない)。

**業務ルール**

- シードスポットは抽選で通常投稿と区別しない（在庫不足時の特別扱いは不要。常にプールに存在することで枯渇を防ぐ）。
- シードには交換（受信権）が発生しない（trigger側にならない）。
- 出典・権利を確認したデータのみ投入する（01 §10。調達方法は運用課題として別途管理）。

## 5. 機能横断の業務ルール

| No | ルール |
| --- | --- |
| G-01 | 文字数は全角半角問わず1文字と数える（Unicodeコードポイント基準。結合文字・絵文字はグラフェム単位）。前後空白はトリム後に判定 |
| G-02 | 日時はUTCで保存し、表示・「1日」の境界判定（PRM-05）はJST基準とする |
| G-03 | 他人のリソースへのアクセスは存在自体を秘匿し404を返す（07 §1.3） |
| G-04 | suspended ユーザーは閲覧系（API-10）と退会（API-12）のみ可。投函・リアクション・通報は403 |
| G-05 | 業務処理と通知は分離し、通知失敗で業務処理をロールバックしない |
