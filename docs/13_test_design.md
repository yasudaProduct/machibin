## 1. はじめに

本書は、まちびんの品質保証方針・テストレベル・テスト環境・重点テストケース（TC-xx）・リリース前チェックリストを定義する。個人開発〜小規模チームの前提で、**リスクの高い箇所へテスト投資を集中させる**リスクベースの戦略をとる。

### 1.1 重点リスク（テスト投資の優先順位）

| 優先 | 領域 | 理由 |
| --- | --- | --- |
| 1 | 交換抽選の除外条件（06 §6.1） | 自分の投稿・受信済み・ブロック相手が配達される事故はサービスの信頼を直接毀損する（FR-04） |
| 2 | 座標丸めの構造的保証（11 §3） | プライバシーは最優先制約（01 §8）。生座標が保存される欠陥は重大インシデント |
| 3 | 冪等性（API-20再送・JOB-02再実行・Webhook再送） | 二重投函・二重配達・二重通知の防止（08 §4.3、10 §6.3） |
| 4 | 認可（10 §7） | 他人リソースの秘匿（404）、suspended/withdrawnの制限、admin境界 |
| 5 | 退会処理（06 §7.1） | 削除・匿名化・残置の区分を誤ると法令対応（NFR-PR05）に直結 |

### 1.2 対象外

Phase 2以降の機能、負荷テストの本格実施（§8の簡易計測のみ行う）、アクセシビリティ検証、ダークモード（05に定義がないため対象外と明示する）。

## 2. テスト戦略

### 2.1 テストレベル構成

ピラミッド型とし、下層ほど厚くする。E2E自動化はスモーク3本に限定し、網羅はリリース前手動チェックリスト（§7）で担保する。

| レベル | 対象 | ツール | DB | 認証 | 実行タイミング |
| --- | --- | --- | --- | --- | --- |
| L1 単体 | `packages/schema` のバリデーション・共有ロジック、`apps/api` のservices純粋部分、認証MW単体 | Vitest | なし | JWKS自己署名（§4.2） | 常時（PR） |
| L1' コンポーネント | モバイルの入力フォーム挙動（05 §6 V-01〜V-10の適用） | jest-expo ＋ React Native Testing Library | なし | モック | 常時（PR） |
| L2 API結合 | Honoアプリ全体（routes→services→DB）。バッチ（jobs）関数 | Vitest（Node上で `app.request()` / ジョブ関数直接呼び出し） | Neonテストブランチ（§4.1） | 認証コンテキスト注入（§4.2） | 常時（PR） |
| L3 E2E | 主要3フローのスモーク（§7.1） | Maestro（staging環境・development build） | staging | Clerk Developmentインスタンス＋SP-05 | リリース前・任意 |
| 手動 | リリース前チェックリスト（§7.2） | 実機 | staging | 実アカウント | リリース毎 |

### 2.2 実行方式の設計判断

- **L2はWorkersランタイムではなくNode上で実行する。** Honoアプリはランタイム非依存であり、`app.request(path, init, env)` で環境変数・モックを注入して結合検証できる。`@neondatabase/serverless`（HTTP）・joseはNode 22でも動作する。Workers固有挙動（Cron起動・カスタムドメイン・キャッシュ）はstagingスモーク（§7）で確認する。
- **バッチ（JOB-02〜04）は `scheduled` ハンドラから呼ばれるジョブ関数を直接呼び出してテストする**（cron式→ジョブのディスパッチは TC-G09 で検証）。
- 外部サービスはネットワーク境界でモックする（§4.3）。実物結合はstagingでの手動確認に限定する。

## 3. テストコード規約

| 項目 | 規約 |
| --- | --- |
| 配置 | L1はソースと同階層の `*.test.ts(x)`。L2は `apps/api/test/` 配下にAPIグループ単位 |
| 命名 | `describe` に対象ID（API-20等）、`it` は日本語で仕様文（例: `it('自分の投稿は抽選から除外される')`） |
| データ | ファクトリ関数（`test/factories.ts`）で生成。マジックナンバー禁止、PRM値は `@machibin/schema` 定数を参照 |
| 座標fixture | geohashセル中心の期待値はライブラリ（ngeohash等）で生成してfixture化する（手書きのハッシュ値をコミットしない） |
| 並列性 | L2（DB使用）はファイル並列を無効化して直列実行する（テストブランチ1本を共有するため。件数増で遅くなったらSP-02で分割を再検討） |

## 4. テスト環境・データ

### 4.1 データベース（SP-02）

| 項目 | 方針 |
| --- | --- |
| 基本 | Neonの**テスト専用ブランチ**を使用する（ローカル: 開発者ごとに `test-<name>` ブランチ、CI: PRごとに `test-<run-id>` ブランチをNeon APIで作成し終了時に削除。02 §9.2のプレビューDB運用と同一基盤） |
| 初期化 | セットアップでdrizzleマイグレーションを適用。各テストは `beforeEach` で対象テーブルを `TRUNCATE ... RESTART IDENTITY CASCADE` |
| 接続 | `DATABASE_URL_TEST` で指定（devブランチとの取り違え防止のため、テストランナーはURL中に `test` を含むことを検証してから実行する） |
| 代替（オフライン時のみ） | `postgis/postgis` Dockerイメージ＋pgドライバ。ドライバ差異があるため、CIでは使用しない |

### 4.2 認証

| レベル | 方針 |
| --- | --- |
| 認証MW単体（L1） | joseで自己署名の鍵ペアを生成し、JWKS取得をモックして10 §5.1の手順1〜4（署名・`iss`・`azp`・`exp`/`nbf`・スキュー5秒）を網羅する。Clerk実物は使わない |
| API結合（L2） | 認証MWをテスト用実装に差し替え、リクエストヘッダ `x-test-user`（テストビルドのみ有効）で `profiles.id`・roleを注入する。**この経路は `TEST_MODE=1` かつテスト実行時のみ組み込まれ、wrangler.tomlの本番/staging設定には存在させない** |
| E2E（L3） | Clerk Developmentインスタンス。OAuth画面の自動操作は行わず、Clerk Backend APIのsign-in tokenによるテストサインイン経路（staging・development buildのみ）を用いる（SP-05） |

### 4.3 外部サービスの扱い

| サービス | L1/L2での扱い | 実物確認 |
| --- | --- | --- |
| Turnstile siteverify | Cloudflare公式のダミーシークレットキーを使用: `1x0000000000000000000000000000000AA`（常に成功）／`2x0000000000000000000000000000000AA`（常に失敗）／`3x0000000000000000000000000000000AA`（token already spent） | stagingで実ウィジェット（SP-01） |
| Expo Push API | fetchモック（送信ペイロードのassert、ticket/receiptの応答注入） | 実機＋自分のトークンで手動（§7.2） |
| Clerk Backend API（ユーザー削除） | クライアントをinterface化しモック（成功・失敗・タイムアウトを注入） | stagingで退会を手動確認 |
| Svix署名 | テスト用シークレットで実ライブラリにより署名を生成して検証を通す（署名検証ロジック自体を実物で試験） | Clerkダッシュボードのテストイベント送信 |
| Sentry | テストでは無効化（DSN未設定） | staging |
