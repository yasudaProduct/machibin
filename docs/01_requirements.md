## 1. はじめに

### 1.1 本書の目的

本書は、位置情報を用いた「おすすめ場所」ランダム交換サービス **まちびん** の要件を定義するものである。本サービスが提供する価値、対象ユーザー、実現すべき機能要件および非機能要件を明確化し、以降の設計・開発工程の基準とすることを目的とする。

### 1.2 対象読者

本サービスの企画者、設計者、開発者、および利害関係者。

### 1.3 用語定義

| 用語 | 定義 |
| --- | --- |
| スポット | ユーザーが投稿する「お気に入りの場所」。位置情報とコメントで構成される。 |
| 投函 | ユーザーがスポットを投稿する行為。手紙を投函するイメージに由来する。 |
| 交換 | 自分のスポットを投函した対価として、他ユーザーのスポットを1件受け取る一連の処理。 |
| 配達 | 交換されたスポットがユーザーに届くまでの遅延演出を含む配信処理。 |
| もらった場所帳 | 受け取ったスポットを地図上にストックするコレクション機能。 |
| シードスポット | 初期のコンテンツ不足（コールドスタート）を補うため運営が投入する投稿。 |
| スナップ | 投稿位置を個人が特定されないよう施設・公共スポット単位に丸める処理。 |

### 1.4 参考資料

- 「まちびん サービスコンセプト案」（事前検討資料）
- 競合調査結果（PhotoSwap、Slowly、レイター、20 Day Stranger、neeboor、Popland 等）

## 2. システム概要

### 2.1 背景と課題

地図・レビューサービス（地図アプリ、グルメサイト等）は「目的があって探す」ためのツールとして成熟している一方、次のような課題が残る。

- 人気度やレビュー点数に基づく検索・レコメンドが中心で、**偶然の出会い（セレンディピティ）** が生まれにくい。
- 上位表示される場所に情報が集中し、個人の熱量ある「小さな名所」が埋もれる。
- 「明日どこへ行こう」「引っ越し先の街を開拓したい」といった、目的が定まっていないニーズに応える手段が乏しい。

### 2.2 サービスコンセプト

自分のお気に入りの場所を1件投函すると、**見知らぬ誰かのお気に入りの場所が1件届く**、場所の「物々交換」サービス。検索でもランキングでもアルゴリズムのレコメンドでもなく、**偶然性**によって、自分では見つけられなかった場所に出会う体験を提供する。

- **タグライン:** 「あなたの日常は、誰かの旅になる。」
- **コアサイクル:** 投函 → 交換 → 受信・リアクション → もらった場所帳への蓄積

### 2.3 提供価値（競合との差別化）

| 観点 | 既存サービス | まちびん |
| --- | --- | --- |
| 発見の方式 | 検索・ランキング・レコメンド | 1対1のランダム交換による偶然の出会い |
| 情報の露出 | 人気の場所ほど多くの人に露出 | 1件ずつ、自分だけに宛てて届く |
| 動機づけ | 点数・人気度 | たった一人の熱量あるコメント |
| ランダム性の質 | 機械的（座標のみ） | 人の推薦（コメント）が乗ったランダム |

> **競合調査からの示唆:** 「場所 × 1対1ランダム交換」の領域は空白であり、最も近いのは写真領域のPhotoSwap、文通領域のSlowlyである。ただし交換型サービス共通の「コールドスタート」「投稿品質の担保」が成否を分けるため、これらを機能要件に織り込む（4章、9章参照）。

### 2.4 ターゲットユーザー / ペルソナ

| ペルソナ | 概要 | 主な利用シーン |
| --- | --- | --- |
| 日常開拓層 | 週末や平日夜の行き先を探している人 | 「明日どこ行こう」の答えを得る |
| 旅行者層 | ガイドブックに載らない一次情報が欲しい人 | 旅先で地元のおすすめに出会う |
| 転入者層 | 引っ越し直後で街に不案内な人 | ご近所交換で新しい街を開拓する |

### 2.5 利用シーン

- 平日夜・週末前：翌日の外出先の参考にする。
- 旅行前・旅行中：訪問予定地域のスポットを受け取る。
- 引っ越し直後：近隣スポットを受け取り生活圏を開拓する。

### 2.6 システム全体構成（概念）

```
[モバイルアプリ (iOS/Android)]
        |  HTTPS/REST(またはGraphQL)
        v
[バックエンドAPI] --- [認証基盤]
        |
        +--- [データベース (位置情報・投稿・交換)]
        +--- [交換マッチング処理 (非同期/バッチ)]
        +--- [配達遅延スケジューラ]
        +--- [プッシュ通知基盤]
        |
[外部サービス連携]
        +--- [地図/ジオコーディングAPI]
        +--- [プッシュ通知配信サービス]
```

> ※本章の構成は概念レベルであり、具体的な技術選定は基本設計工程で決定する。

## 3. スコープ

### 3.1 開発スコープ（フェーズ分け）

本サービスは段階的にリリースする。各機能の優先度を以下のフェーズで定義する。

| フェーズ | 位置づけ | 主な内容 |
| --- | --- | --- |
| Phase 1（MVP） | 中核体験の検証 | 投函・交換・受信・リアクション・もらった場所帳・通報/ブロック |
| Phase 2 | 体験の拡張 | 距離モード選択・お題交換・配達遅延演出の高度化 |
| Phase 3 | 発展 | 旅先モード・地域公式ポスト（自治体等タイアップ）・プレミアム |

### 3.2 対象外事項（本フェーズでは扱わない）

- ユーザー間のダイレクトメッセージ（DM）機能。
- リアルタイムチャット。
- スポットのランキング表示・いいね数の公開。
- ECおよび予約・決済連携（プレミアム課金を除く）。
- Webブラウザ版クライアント。

### 4.2 機能詳細

#### FR-01 会員登録・認証

- ユーザーはアカウントを新規登録できること。登録には最小限の情報（認証手段、ニックネーム）のみを求め、本名・写真は必須としない。
- ユーザーはログイン・ログアウトができること。
- ユーザーは退会でき、退会時は本人の投稿・受信データの取り扱い方針（削除または匿名化）に従うこと。
- 未成年の利用可否および年齢確認方針を定めること（詳細は基本設計で決定）。

#### FR-02 プロフィール管理

- ユーザーはニックネームおよびアバターを設定・変更できること。
- 居住エリアは**市区町村レベル**までとし、番地レベルの情報は保持しないこと。
- プロフィールに設定できる自己紹介は短文（ひとこと程度）に留めること。

#### FR-03 スポット投函

- ユーザーは、GPSによる現在地取得、または地図上のピン指定により場所を選択できること。
- ユーザーはスポットに対しコメント（短文）を必須で入力すること。
- **投稿品質担保のため、コメントには最低文字数を設けること**（推奨：全角20文字以上。値は運用で調整可能とする）。
- ユーザーは場所のカテゴリ（例：カフェ／公園／飲食店／その他）を選択できること。
- 投稿位置は**施設・公共スポット単位にスナップ**し、個人宅が特定できる精度を持たせないこと（自宅推定の防止）。
- 明らかに不適切な位置（自宅を推定させる住宅地の座標等）への投稿を抑制する仕組みを検討すること。

#### FR-04 ランダム交換

- ユーザーは、自分のスポットを1件投函することを条件に、他ユーザーのスポットを1件受け取る権利を得ること（交換の1対1性）。
- 交換相手・受信スポットはランダムに割り当てること。
- 自分自身の投稿、過去に受信済みの投稿、および通報・ブロック関係にある相手の投稿は割当対象から除外すること。
- 交換可能な在庫が不足する場合は、**シードスポット（FR-10）** を割当対象に含めることで体験の枯渇を防ぐこと。
- 交換範囲（距離）はPhase 2で選択可能とする（FR-11）。Phase 1では既定範囲（完全ランダム）とする。

#### FR-05 受信・配達

- 割り当てられたスポットは、**即時表示ではなく配達遅延演出**を伴って届くこと（「翌朝ポストに入っている」体験）。
- 配達までの所要時間は、Phase 2以降で送信者と受信者の距離に応じて変動させること（遠いほど時間がかかる）。Phase 1では固定の遅延時間としてもよい。
- 配達完了時にユーザーへ通知すること（FR-09）。
- 受信スポットには、場所名・位置・カテゴリ・コメント・（任意で）差出人エリア（市区町村レベル）を表示すること。差出人個人は特定されないこと。

#### FR-06 リアクション

- ユーザーは受信スポットに対し「行ってみたい」「行ってきた」の2種のリアクションを付与できること。
- 「行ってきた」の場合のみ、短文の報告コメントを添付できること（それ以外の自由な返信・DMは提供しない）。
- リアクションは差出人へ通知されること（FR-09）。ただしランキングや累計いいね数として公開しないこと。

#### FR-07 もらった場所帳

- ユーザーは受信したスポットを地図上にストックし、一覧・地図の両形式で閲覧できること。
- ユーザーは各スポットに訪問ステータス（未訪問／訪問済み）を記録できること。
- 訪問済みスポットにはスタンプ等の視覚的な達成表現を付与すること。
- 自分の投稿が「行ってきた」された累計回数を、本人のみが確認できる形で表示してもよい（他者へのランキング公開はしない）。

#### FR-08 通報・ブロック

- ユーザーは不適切なスポットまたはユーザーを通報できること。
- 通報されたユーザーとは、以降マッチング（交換割当）を行わないこと（マッチ永久除外）。
- 通報の類型（不適切な内容、位置の悪用、迷惑行為等）を定義し、運営が確認・対処できること。
- 一定の通報を受けた投稿・アカウントを自動または手動で非表示・停止できること。

#### FR-09 通知

- 次のイベント発生時にプッシュ通知を行うこと：交換成立、スポットの配達完了、受信スポットへのリアクション着信。
- ユーザーは通知の種類ごとに受信可否を設定できること。

#### FR-10 シードスポット投入（運営機能）

- 運営者は、交換在庫の補填やサービス初期の体験担保を目的にスポットを投入できること。
- シードスポットも通常投稿と同一の表示・品質基準（コメント・位置スナップ）に従うこと。

#### FR-11 距離モード選択（Phase 2）

- ユーザーは交換範囲を「ご近所交換（近距離）」「遠距離交換」「完全ランダム」から選択できること。
- 距離のしきい値は運用で調整可能とすること。

#### FR-12 お題交換（Phase 2）

- 運営は週替わり等のテーマ（例：「雨の日に行く場所」「ベンチが最高な場所」）を設定できること。
- ユーザーは選択したテーマに沿ってスポットを投函し、同テーマの相手と交換できること。

#### FR-13 旅先モード（Phase 3）

- ユーザーが旅行先で位置情報を有効にした場合、その地域の住民が投稿したスポットを優先的に受信できること。

#### FR-14 プレミアム（Phase 3）

- 有料ユーザーは、交換回数の拡張、遠距離範囲の指定、テーマ作成等の追加機能を利用できること。
- 広告レコメンドは、偶然性への信頼を損なうため導入しない方針とする。

### 4.3 主要ユースケース

**UC-01 場所を交換する（コアフロー）**

1. ユーザーがアプリを起動する。
2. ユーザーがお気に入りの場所を選び、コメントを入力して投函する（FR-03）。
3. システムが投函を受理し、交換対象を1件ランダムに割り当てる（FR-04）。
4. システムが配達遅延演出を経て、受信スポットをユーザーに届ける（FR-05）。
5. ユーザーが配達完了通知を受け取り、受信スポットを閲覧する。
6. ユーザーがリアクションを付与する（FR-06）。
7. 受信スポットが「もらった場所帳」に蓄積される（FR-07）。

**UC-02 受け取った場所を訪問し記録する**

1. ユーザーが「もらった場所帳」から行きたいスポットを選ぶ。
2. ユーザーが実際に訪問する。
3. ユーザーが訪問ステータスを「訪問済み」に更新し、スタンプを得る（FR-07）。
4. 必要に応じて「行ってきた」リアクションと報告コメントを付与する（FR-06）。

**UC-03 不適切な投稿を通報する**

1. ユーザーが受信スポットに不適切な内容を認める。
2. ユーザーが通報を行う（FR-08）。
3. システムが当該相手をマッチ対象から除外し、運営が内容を確認・対処する。

## 5. 非機能要件

### 5.1 性能要件

| ID | 要件 |
| --- | --- |
| NFR-P01 | 主要画面（ホーム・投函・場所帳）の表示は、通常のモバイル回線環境で概ね3秒以内に完了すること。 |
| NFR-P02 | 交換割当および配達は非同期処理を許容し、投函操作自体は待ち時間なく完了すること。 |

### 5.2 可用性要件

| ID | 要件 |
| --- | --- |
| NFR-A01 | サービスの稼働率は99.5%以上を目標とすること（計画メンテナンスを除く）。 |
| NFR-A02 | 計画メンテナンス時は事前告知を行い、影響を最小化すること。 |

### 5.3 セキュリティ要件

| ID | 要件 |
| --- | --- |
| NFR-S01 | クライアント・サーバ間の通信はすべてTLSで暗号化すること。 |
| NFR-S02 | 認証情報は適切にハッシュ化・保護し、平文で保持しないこと。 |
| NFR-S03 | 不正アクセス・スパム投稿・自動化投稿（Bot）を検知・抑制する仕組みを設けること。 |
| NFR-S04 | 個人を特定し得る情報へのアクセスを最小権限で制御すること。 |

### 5.4 プライバシー要件（位置情報の取り扱い）※重点項目

| ID | 要件 |
| --- | --- |
| NFR-PR01 | 投稿位置は施設・公共スポット単位にスナップし、番地レベルの精度で保存・表示しないこと（自宅特定の防止）。 |
| NFR-PR02 | 差出人の個人情報を受信者に開示しないこと。開示するエリア情報は市区町村レベルまでとすること。 |
| NFR-PR03 | 位置情報の取得はユーザーの明示的な許可に基づくこと。許可しない場合でも地図ピン指定で投稿できること。 |
| NFR-PR04 | 個人情報保護法および関連ガイドラインを遵守すること。プライバシーポリシーを整備・掲示すること。 |
| NFR-PR05 | ユーザーは自身のデータの削除（退会時を含む）を要求できること。 |

### 5.5 拡張性・保守性

| ID | 要件 |

## 8. 前提・制約条件

- 本サービスの中核体験（1対1のランダム交換）は、一定数の投稿者が存在してはじめて成立する。初期のコンテンツ不足を補うため、シードスポット投入と地域を絞ったローンチを前提とする。
- 位置情報を扱うサービスであるため、プライバシー保護（自宅特定防止・匿名性）を最優先の制約とする。
- ユーザー間の直接的なコミュニケーション（DM・チャット）は提供しない。交流はリアクションの範囲に限定する。
- 広告レコメンドは、偶然性への信頼を損なうため導入しない。

## 9. リスクと課題

| No | リスク／課題 | 内容 | 対応方針 |
| --- | --- | --- | --- |
| R-01 | コールドスタート | 投稿者が少ないと交換できず体験が成立しない。 | シードスポット投入（FR-10）、地域・コミュニティ単位での狭く濃いローンチ。 |
| R-02 | 投稿品質の低下 | 内容の薄い投稿や不適切投稿が体験を損なう。 | コメント最低文字数（FR-03）、通報とマッチ永久除外（FR-08）、運営確認（NFR-O01）。 |
| R-03 | プライバシー侵害 | 位置情報から自宅等が特定される懸念。 | 施設単位スナップ（NFR-PR01）、エリアは市区町村まで（NFR-PR02）。 |
| R-04 | 安全性（悪用） | 位置情報の悪用、迷惑行為。 | DM非提供、配達遅延による即時特定の困難化、通報・ブロック。 |
| R-05 | 継続率の低下 | 交換の目新しさが薄れ利用が減る。 | 配達演出の価値、お題交換・旅先モードによる体験の更新。 |
| R-06 | 収益化の難しさ | 広告非導入方針での収益確保。 | プレミアム機能（FR-14）、地域公式ポスト等のタイアップ。 |
